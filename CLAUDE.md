# DM Screen

A D&D dashboard for in-person games with kids aged 10–12 (Lego minis on a projected map). The owner is Pastor Nick at Rochester Christian Church. Use 2024 D&D rules and SRD monsters.

## Design rules
- Simple and easy to navigate comes first. A kid or a first-time DM should never get lost.
- No player accounts. Players join with a game code and a first name only.
- Escape every saved value before putting it in HTML (`esc()`).
- Text in the UI is plain and friendly. No jargon.

## Layout
- `web/index.html` is the **source of truth** for the DM page. It is one file of vanilla JS, no build step.
- `local-edition/dm.html` must be an exact copy of `web/index.html`. After every edit run `cp web/index.html local-edition/dm.html`.
- `local-edition/player.html` is the player page. It works locally (EventSource) and online (WebSocket), detected from the `/s/<CODE>/` path.
- `local-edition/server.py` is the offline LAN server. `local-edition/seed.json` is the starter data.
- `online/` is the Cloudflare edition: `src/worker.js` (routes), `src/session.js` (one SQLite Durable Object per game code), `public/` (landing page plus synced copies), R2 bucket `dm-screen-pictures` for images.
- `online/public/dm.html` and `play.html` are generated by `npm run sync`. Do not edit them.
- `camera-kit/` is the Lego table camera. It is not connected to the DM Screen yet.
- `index.html` at the repo root redirects GitHub Pages to `web/`.

## Commands (run from `online/`)
- `npm run dev` starts wrangler locally. It prints the port (usually 8787).
- `npm test` syncs, then runs `scripts/test.mjs`. It checks against `BASE`, default `http://localhost:8799`, so set `BASE` to the dev port.
- `npm run deploy` syncs and deploys. Live site: https://dm-screen.nchlshodge.workers.dev
- Test against the live site with `BASE=https://dm-screen.nchlshodge.workers.dev node scripts/test.mjs`.

## How it works
- Game codes look like `WOLF-42`. The DM key is stored as a SHA-256 hash and sent as `X-DM-Key` (HTTP) or the `dm.<key>` WebSocket subprotocol. Players use a token (`p.<token>`). The view-only table link has its own key (`tv.<key>`, `X-Table-Key`).
- The DM page talks through an adapter: `makeAdapter(docs, upload)` with `lanConnect()`, `onlineConnect()` or `tableConnect()`.
- The table viewer only gets the map, combat, heroes, the dice log (secret rolls removed) and the handout on screen. Never monsters, tables, chat or players. Keep that filter (`tvFilter` in `session.js`) strict when adding data.
- A player receives their own whole character record, so nothing in a character is truly secret from that player.
- Imported character files are sanitized (`cleanHero`): whitelisted key pattern, size caps, always new ids. New text fields on a character pass through export and import automatically.

## Before you ship a change
- Test at desktop width and at 390px wide. Zero console errors.
- A security hook on the Write tool can mistake the SQL helper call in `session.js` for a shell command. The file uses a `q()` wrapper for that reason. If a Write is blocked, write the file with a Bash heredoc.
- After an update, refresh both the DM window and the table (second) window. Each loads its own copy of the page, so a window left open keeps the old version. Check this before reporting a new feature as "not showing".
- Work on a feature branch and open a PR. Merge and deploy only when Nick says so.

## Known limits
- Codes can be guessed (about 18,000 combinations). Defenses: 12-player cap, per-game guess throttle, the DM can remove players.
- Shop prices and magic item rarities were written from memory and are unverified.
- Scripture Scout (a separate project) shares the Cloudflare account. Do not touch it.
